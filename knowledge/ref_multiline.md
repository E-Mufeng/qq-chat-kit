# 多线并行管理：同时 3+ 对象不串号

> 用途：军师在内部分析层判断"当前这条该用哪个对象的档案、绝不能串"。这是代聊军师的生命线——串号=翻车。

## 1. 为什么必须隔离
- 聊天代聊时，bot 以"你"的身份发言。一旦把 A 的昵称/约定/梗发到 B 那里，对方立刻识破"你不是一个人/你在撩多个"，信任归零。
- 三条绝对红线：
  1. 不跨对象提人名/昵称/专属称呼。
  2. 不跨对象用只有另一人懂的梗、回忆、约定。
  3. 不暴露"我同时在聊别人"的任何措辞（"刚和别人聊完""你们女生都…"）。

## 2. ID / 代号体系
- 每个对象一个不可混淆的 `partner_id`（QQ号）。显示层用代号（A/B/C 或真实备注名），但内部全走 partner_id。
- 档案字段（见 memory_store）：`display_name, stage, interests, last_topic, emotional_state, dont_repeat[], key_events[], created_at`。
- 切换对象时，只加载该 partner_id 的档案+该对象滚动窗口，绝不混入他人。

## 3. 状态机（每人独立）
```
初识 → 破冰 → 升温 → 暧昧 → 确认/淘汰
         ↑________冷却/复活________↓
```
- 每对象当前处于哪个状态写进档案；回复策略随状态切换（初识轻聊、升温加张力、暧昧上邀约）。
- 状态错配=穿帮（对刚认识的人用暧昧语气、对暧昧的人还破冰）。

## 4. 时间分配矩阵
- A:B:C ≈ 5:3:2。高意愿优先，但每天给低优先级对象也留 1 次轻互动维持温度。
- 用"上次互动时间"驱动：超过 36h 无互动的活跃对象，下次会话先一句轻钩子回暖。

## 5. 发前自检 checklist（每条消息生成后、发送前）
- [ ] 这条有没有提到任何别人的名字/昵称？
- [ ] 用了只有另一个对象懂的梗/回忆/内部约定吗？
- [ ] 有没有"你们/女生都/刚和别人"这类暴露并行的词？
- [ ] 这条的风格/称呼和该对象档案一致吗（别把对A的称呼发B）？
- 任一为"是" → 丢弃重写。

## 6. 记忆分库实现要点
- 持久层按 partner_id 分表/分键，读取严格限定 `WHERE partner_id = ?`。
- 上下文拼装：`[用户本人档案] + [该对象档案] + [该对象最近N轮]` —— 其余对象的数据物理上不进这条 prompt。
- debug 验收：A/B/C 各聊不同话题各 10 轮，断言 A 的回复上下文里不出现 B/C 的任何专有信息。
